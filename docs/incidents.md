## INC-001 — Postgres лежал неделю без алерта (17–24 мая 2026)

### Краткая сводка

С 17 мая по 24 мая 2026 (около 7 дней) docker-контейнер с PostgreSQL
не запускался после рестарта сервера. Сайт `questdating.ru` продолжал
отвечать `HTTP 200` на главной странице (Nuxt отдавал SSR с кэшем
`swr: 300`), а API возвращало 500 на половине эндпоинтов, либо
закэшированные ответы 5-минутной давности через in-memory cache в
`statsService.js`. Существующий мониторинг (`monitor.sh`) ни одного
алерта не отправил, потому что проверял только HTTP-код главной.

Инцидент обнаружен случайно при попытке задеплоить новую правку
(закрытие задачи 1.1.1 — hardcoded email).

### Хронология

| Время (MSK) | Событие |
|---|---|
| 17 мая ~22:39 | docker-postgres корректно остановлен (вероятно `docker compose down` или перезагрузка docker) |
| 18 мая 01:40 | Сервер VPS перезагружен (PM2 восстанавливал процессы). Docker daemon попытался поднять контейнеры с `restart: unless-stopped`. Postgres-контейнер упал с exit 127 при попытке смонтировать `./database/dump.sql`. |
| 18 мая — 24 мая | Контейнер крутится в Restarting/Exited. Сайт отдаёт SSR-кэш и кэшированные API-ответы. Мониторинг видит HTTP 200 на главной → status UP → алертов нет. |
| 24 мая ~21:00 | Деплой правки 1.1.1 на прод. После `docker compose restart server` в логах обнаружены `Connection terminated due to connection timeout` → начато расследование. |
| 24 мая ~21:39 | После удаления пустой директории `database/dump.sql/` и закомментирования соответствующего bind-mount в `docker-compose.yml` postgres-контейнер успешно запущен. |
| 24 мая ~21:42 | Сервер переподключился к БД, сайт полностью восстановлен. |

| 25 мая ~01:00 | Обновлён `monitor.sh` — теперь проверяет `/health` напрямую на backend, минуя nginx, Nuxt-прокси и кэш в `cache.js`. |

### Корневые причины

1. **Docker bind-mount несуществующего файла создаёт директорию.**
   В `docker-compose.yml` была строка:
   ```yaml
   - ./database/dump.sql:/docker-entrypoint-initdb.d/init.sql
   ```
   Файл `dump.sql` отсутствовал в репозитории (это и есть задача 1.2.6
   из плана — сгенерировать). При первой попытке монтирования Docker
   тихо создал на хосте **директорию** с именем `dump.sql`. На следующих
   рестартах bind-mount пытался смонтировать директорию в контейнер на
   место файла → exit 127.

2. **Мониторинг проверял неправильную метрику.**
   `monitor.sh` делал `curl https://questdating.ru` и проверял HTTP-код.
   Главная страница SSR с `swr: 300` — Nuxt продолжал отдавать
   закэшированный HTML, статус 200 был стабильным. Никакого реального
   сигнала о состоянии БД в этой проверке не было.

3. **Backend кэширует API-ответы на 5 минут без проверки источника.**
   В `server/src/services/statsService.js` и `cache.js (getOrSet)`
   популярные endpoints (`/api/stats`, `/api/templates/featured`,
   `/api/reviews/featured`) кэшируются в in-memory `Map` на 5 минут.
   Когда БД лежала, кэш продолжал отдавать данные, ошибки появлялись
   только на endpoints без кэша (заказы и т.п. — но они вызываются
   реже, и тоже не мониторились).

4. **Health-endpoint не проверял БД.**
   Старый `/health` возвращал просто `{ status: "OK", uptime }`.
   Это правда про процесс Node.js, но не про систему в целом.

### Что обнаружили в процессе расследования

- В директории `/home/questdating/database/` файла `dump.sql` нет в
  истории git. Был добавлен в `.gitignore` пустым шаблоном.
- В docker volume `questdating_postgres_data` лежат полные production-
  данные (63 МБ): 13 заказов, 7 шаблонов квестов, отзывы, всё на месте.
- В host-системе кто-то поднимал PostgreSQL отдельно (вне Docker) с
  тестовой БД `quest_dating` — 1 заказ Анны Ивановой от 6 февраля.
  Это **не production-данные**, источник пока не выяснен. Сервер к
  host-postgres не подключался (DB_HOST=postgres в docker-compose).
- Утёкший GitHub PAT обнаружен в `git remote -v` (отозван 24 мая).
- `.gitignore` содержал `vscode-testbackups/` вместо двух отдельных
  строк `.vscode-test` и `backups/` (исправлено отдельно).

### Что сделано для устранения

1. Удалена пустая директория `database/dump.sql/` на проде.
2. Закомментирована строка bind-mount в `docker-compose.yml` (PR #4).
3. Health-endpoint переписан с реальной проверкой БД через `pool.query('SELECT 1')` + `Cache-Control: no-store`. Возвращает 200 + `db:connected` или 503 + `db:disconnected` (PR #2/#3).
4. `monitor.sh` переписан: бьёт прямо в `http://127.0.0.1:5001/health`,
   парсит JSON, проверяет `db:connected`, шлёт алерт с конкретной
   причиной (PR #4).
5. Создан docker-volume snapshot:
   `backups/docker-volume-snapshot-2026-05-25.tar.gz` (12 МБ сжатые).

### Уроки

- **Bind-mount файлов в docker-compose опасен.** Если файл может
  отсутствовать — либо использовать `:ro`, либо отказаться от
  bind-mount в пользу образа/init-скрипта через `command:`. Сейчас
  до момента решения 1.2.6 эта строка закомментирована.
- **Endpoint для мониторинга должен реально дёргать критичные
  зависимости.** Просто 200 OK без проверки БД — самообман.
- **Кэширование на бэкенде маскирует падения.** Это и фича (отказо-
  устойчивость), и баг (отсутствие сигнала). Минимум: метрика
  "сколько последних ответов из кэша" в дашборде. Идеально:
  отдельный канал доставки реального состояния (этот health).
- **Мониторинг должен бить мимо всех проксей и кэшей.** Идёт прямо
  в процесс backend на `127.0.0.1`.
- **Чистый git-репозиторий обязателен.** Без него любой `git pull`
  на проде становится мини-расследованием.
