## INC-001 — Postgres лежал неделю без алерта (17–24 мая 2026)

### Краткая сводка

С 17 мая по 24 мая 2026 (около 7 дней) docker-контейнер с PostgreSQL
не запускался после рестарта сервера. Сайт `questdating.ru` продолжал
отвечать `HTTP 200` на главной странице (Nuxt отдавал SSR с кэшем
`swr: 300`), а API возвращало 500 на половине эндпоинтов, либо
закэшированные ответы 5-минутной давности через in-memory cache в
`statsService.js`. Существующий мониторинг (`monitor.sh`) ни одного
алерта не отправил, потому что проверял только HTTP-код главной.

Инцидент обнаружен случайно при попытке задеплоить новую правку
(закрытие задачи 1.1.1 — hardcoded email).

### Хронология

| Время (MSK) | Событие |
|---|---|

| 18 мая 01:40 | Сервер VPS перезагружен (PM2 восстанавливал процессы). Docker daemon попытался поднять контейнеры с `restart: unless-stopped`. Postgres-контейнер упал с exit 127 при попытке смонтировать `./database/dump.sql`. |
| 18 мая — 24 мая | Контейнер крутится в Restarting/Exited. Сайт отдаёт SSR-кэш и кэшированные API-ответы. Мониторинг видит HTTP 200 на главной → status UP → алертов нет. |
| 24 мая ~21:00 | Деплой правки 1.1.1 на прод. После `docker compose restart server` в логах обнаружены `Connection terminated due to connection timeout` → начато расследование. |
| 24 мая ~21:39 | После удаления пустой директории `database/dump.sql/` и закомментирования соответствующего bind-mount в `docker-compose.yml` postgres-контейнер успешно запущен. |

### Корневые причины

1. **Docker bind-mount несуществующего файла создаёт директорию.**
   В `docker-compose.yml` была строка:
   ```yaml
   - ./database/dump.sql:/docker-entrypoint-initdb.d/init.sql
   ```
   Файл `dump.sql` отсутствовал в репозитории (это и есть задача 1.2.6
   из плана — сгенерировать). При первой попытке монтирования Docker
   тихо создал на хосте **директорию** с именем `dump.sql`. На следующих
   рестартах bind-mount пытался смонтировать директорию в контейнер на
   место файла → exit 127.

2. **Мониторинг проверял неправильную метрику.**
   `monitor.sh` делал `curl https://questdating.ru` и проверял HTTP-код.
   Главная страница SSR с `swr: 300` — Nuxt продолжал отдавать
   закэшированный HTML, статус 200 был стабильным. Никакого реального
   сигнала о состоянии БД в этой проверке не было.

3. **Backend кэширует API-ответы на 5 минут без проверки источника.**
   В `server/src/services/statsService.js` и `cache.js (getOrSet)`
   популярные endpoints (`/api/stats`, `/api/templates/featured`,
   `/api/reviews/featured`) кэшируются в in-memory `Map` на 5 минут.
   Когда БД лежала, кэш продолжал отдавать данные, ошибки появлялись
   только на endpoints без кэша (заказы и т.п. — но они вызываются
   реже, и тоже не мониторились).

4. **Health-endpoint не проверял БД.**
   Старый `/health` возвращал просто `{ status: "OK", uptime }`.
   Это правда про процесс Node.js, но не про систему в целом.

### Что обнаружили в процессе расследования

В первые часы после обнаружения:

- В директории `/home/questdating/database/` файла `dump.sql` нет в
  истории git. Был добавлен в `.gitignore` пустым шаблоном.
- В docker volume `questdating_postgres_data` лежат полные production-
  данные (63 МБ): 13 заказов, 7 шаблонов квестов, отзывы, всё на месте.
- В host-системе кто-то поднимал PostgreSQL отдельно (вне Docker) с
  тестовой БД `quest_dating` — 1 заказ Анны Ивановой от 6 февраля.
  Это **не production-данные**, источник пока не выяснен. Сервер к
  host-postgres не подключался (DB_HOST=postgres в docker-compose).
- Утёкший GitHub PAT обнаружен в `git remote -v` (отозван 24 мая).
- `.gitignore` содержал `vscode-testbackups/` вместо двух отдельных
  строк `.vscode-test` и `backups/` (исправлено отдельно).

При расширенной зачистке инфраструктуры (25–26 мая, см. раздел
"Долгосрочный follow-up") вскрылись новые рудименты pre-Docker-эпохи:

- **PM2-фантом.** На хосте 7 дней крутился systemd-юнит `pm2-root.service`
  и один процесс в `pm2 list` с именем `quest-dating-api`, который
  пытался поднять `/home/questapp/quest-dating/server/src/server.js` —
  путь от **старой** кодовой базы (которой больше нет; код переехал
  в `/home/questdating/` ещё при миграции на Docker в феврале 2026).
  PM2 пытался стартовать процесс при boot 18 мая, упал, и с тех пор
  висел в зомби-состоянии `status: online, pid: N/A`. То есть, у нас
  был и второй слой "мониторинга", который тоже ничего не сообщал.
- **Дублирующая установка Node 20 через apt.** Помимо активной nvm-
  установки `~/.nvm/versions/node/v20.20.0`, в системе была вторая
  через `apt`/NodeSource (`nodejs 20.20.0-1nodesource1`, бинарь
  `/usr/bin/node` весом 97 МБ). PATH приоритезировал nvm, поэтому
  apt-версия не использовалась, но лежала мёртвым грузом и могла
  всплыть в скриптах с явным путём.
- **PM2 тоже в двух копиях.** При попытке удалить `npm uninstall -g pm2`
  через активный nvm-npm убрал nvm-копию, но в `/usr/lib/node_modules/pm2`
  оставалась системная установка с симлинками `/usr/bin/pm2`, `pm2-dev`,
  `pm2-docker`, `pm2-runtime`. Удалена вручную.
- **Nuxt 4.4 vs Node 20.** При выполнении npm audit fix в client-nuxt
  пакеты Nuxt 4.4.6 обновились, и их `engines` стали требовать Node
  `^22.12.0`. На VPS — Node 20.20.0 и в nvm, и в Docker-контейнерах.
  Работало "по факту", но `EBADENGINE` warnings сыпались при каждом
  `npm install`. Закрыто отдельно (см. follow-up).

### Что сделано для устранения

1. Удалена пустая директория `database/dump.sql/` на проде.
2. Закомментирована строка bind-mount в `docker-compose.yml` (PR #4).
3. Health-endpoint переписан с реальной проверкой БД через `pool.query('SELECT 1')` + `Cache-Control: no-store`. Возвращает 200 + `db:connected` или 503 + `db:disconnected` (PR #2/#3).
4. `monitor.sh` переписан: бьёт прямо в `http://127.0.0.1:5001/health`,
   парсит JSON, проверяет `db:connected`, шлёт алерт с конкретной
   причиной (PR #4).
5. Создан docker-volume snapshot:
   `backups/docker-volume-snapshot-2026-05-25.tar.gz` (12 МБ сжатые).

### Уроки

- **Bind-mount файлов в docker-compose опасен.** Если файл может
  отсутствовать — либо использовать `:ro`, либо отказаться от
  bind-mount в пользу образа/init-скрипта через `command:`. Сейчас
  до момента решения 1.2.6 эта строка закомментирована.
- **Endpoint для мониторинга должен реально дёргать критичные
  зависимости.** Просто 200 OK без проверки БД — самообман.
- **Кэширование на бэкенде маскирует падения.** Это и фича (отказо-
  устойчивость), и баг (отсутствие сигнала). Минимум: метрика
  "сколько последних ответов из кэша" в дашборде. Идеально:
  отдельный канал доставки реального состояния (этот health).
- **Мониторинг должен бить мимо всех проксей и кэшей.** Идёт прямо
  в процесс backend на `127.0.0.1`.
- **Чистый git-репозиторий обязателен.** Без него любой `git pull`
  на проде становится мини-расследованием.
- **Рудименты pre-Docker-эпохи опаснее, чем кажутся.** PM2-юнит,
  apt-Node, дубль PM2 в /usr/lib — каждый из них сам по себе ничего
  не делал, но создавал "теневые слои", которые усложняли диагностику
  и могли всплыть в неожиданный момент. После миграции архитектуры
  нужно явно проводить ревизию того, что было нужно "до", и убирать.

## INC-002 — Прод упал 502 при деплое nginx-конфига (28 мая 2026)

### Краткая сводка

При попытке задеплоить обновлённый `nginx/nginx.conf` (с новым endpoint
`/health`, см. ниже контекст) прод `questdating.ru` отдал `HTTP 502 Bad
Gateway`. Downtime — несколько минут, пока не откатились на бэкап.
`monitor.sh` корректно поймал падение и прислал Telegram-алерт
("questdating.ru НЕДОСТУПЕН! Главная: HTTP 502").

Две независимые ошибки сложились в падение:
1. Конфиг в git-репо (`nginx/nginx.conf`) был **фиктивным** — написан под
   nginx-в-Docker, никогда не применялся. При деплое затёр рабочий конфиг.
2. Бэкап рабочего конфига был сохранён **внутри** `/etc/nginx/sites-enabled/`,
   из-за чего стал вторым активным конфигом и участвовал в путанице
   маршрутизации.

### Контекст: зачем вообще трогали nginx

После закрытия задачи 1.2.6 (БД и dump.sql) при проверке выяснилось, что
`https://questdating.ru/health` отдаёт 404. Внутренний health
(`127.0.0.1:5001/health`, куда бьёт monitor.sh) работал — но публичный URL
через nginx не был настроен на проксирование `/health` к Express. При
попытке это починить и всплыла вся цепочка.

### Хронология (MSK)

| Время | Событие |
|---|---|
| ~23:40 | Снят страховочный бэкап БД перед 1.2.6. Применён dump.sql + docker-compose. Прод жив, 13 заказов на месте. |
| ~23:42 | Проверка `https://questdating.ru/health` → 404. Начато расследование. |
| ~23:48 | Найдено: `nginx/nginx.conf` в репо написан для Docker-nginx (`proxy_pass http://client:3000`), но на проде nginx на хосте с другим конфигом в `/etc/nginx/sites-enabled/quest-dating`. |
| ~23:52 | Сделан бэкап текущего конфига — **ошибочно в `sites-enabled/`** (`quest-dating.backup-20260527`). Применён конфиг из репо (с IP `89.124.90.154`). |
| ~23:53 | Прод отдаёт 502. Telegram-алерт от monitor.sh. |
| ~23:55 | Откат: восстановлен рабочий конфиг из бэкапа. `nginx -t` → ok, `reload`. Сайт встал (200). |
| 28 мая ~10:00 | Полная диагностика: собраны все `listen`/`server_name`, `dig`, `ls sites-enabled`. Выявлены обе корневые причины. |
| ~10:15 | Подготовлен правильный конфиг = реальный прод + только блок `/health`. Сверен diff'ом. |
| ~10:20 | Применён по корректной процедуре (бэкап в `/tmp`, `nginx -t`, `reload`). `/health`, `/api/stats`, `/` — все 200. |

### Корневые причины

1. **Конфиг в репо разошёлся с реальностью (был фикцией).**
   `nginx/nginx.conf` в репозитории был написан под запуск nginx внутри
   Docker-контейнера (`proxy_pass http://client:3000`, `http://server:5000`,
   полный top-level `http {}` блок). Но фактически nginx работает на хосте
   как systemd-сервис, и использует совсем другой конфиг
   (`/etc/nginx/sites-enabled/quest-dating` с `proxy_pass http://127.0.0.1`).
   Эти два жили параллельно, репо-версия никогда не применялась. При деплое
   она затёрла рабочую.

2. **Неверный IP в `listen`.** Деплоенный конфиг слушал `89.124.90.154`.
   Этот IP висит на интерфейсе (`ip addr` его показывает), но публичный
   трафик домена идёт на `146.103.111.12` (туда резолвится DNS). nginx,
   слушая не тот IP, не отвечал на реальные запросы → 502.

3. **Бэкап в активной директории nginx.** Бэкап рабочего конфига был
   сохранён как `/etc/nginx/sites-enabled/quest-dating.backup-20260527`.
   nginx инклюдит `sites-enabled/*` целиком — **все** файлы, включая
   `.backup-*`. В результате одновременно были активны два server-блока
   для `questdating.ru` на разных IP, что усложнило диагностику и
   маскировало, какой конфиг реально отвечает.

### Что сделали для устранения

1. Немедленный откат на бэкап рабочего конфига — сайт встал за ~2 минуты.
2. Полная диагностика реального состояния: `nginx -T`, `dig`, `ip addr`,
   `ls -la sites-enabled/` — собрана достоверная картина вместо догадок.
3. В репо положен **фактический** рабочий конфиг прода + точечно добавлен
   только блок `location = /health` (PR #29). Diff'ом подтверждено, что
   функциональные директивы прода не тронуты.
4. Бэкап перенесён из `sites-enabled/` (на этапе восстановления —
   в `sites-available/`, далее процедура предписывает `/tmp`).
5. Применение по корректной процедуре: бэкап в `/tmp`, `nginx -t` до
   `reload`, проверка трёх endpoint после.

### Уроки

- **Конфиг инфраструктуры в репо должен быть копией реальности, не фикцией.**
  Если в репо лежит конфиг, который «когда-нибудь применим» — это бомба.
  Перед деплоем инфра-конфига нужно снять актуальную версию с прода и
  свериться diff'ом, а не доверять тому, что лежит в git.
- **Бэкап nginx-конфига — только вне зоны инклюда.** `/tmp` или
  `/root/backups`, никогда не в `sites-enabled/` или `sites-available/`
  (последнее безопаснее, но всё равно мусорит). nginx читает всю папку.
- **`nginx -t` перед каждым `reload` — железное правило.** Именно эта
  проверка предотвратила второе падение при восстановлении.
- **Привязка `listen` к конкретному IP хрупка.** Машина имеет несколько
  IP на интерфейсе; DNS указывает на один. При рассинхроне (переезд,
  смена IP) — мгновенный 502. Кандидат на `listen 443 ssl` без IP или
  явный `default_server` (см. follow-up).
- **monitor.sh сработал штатно.** Поймал 502 и прислал алерт — то, ради
  чего его переписывали после INC-001. Подтверждение, что мониторинг
  теперь рабочий.
