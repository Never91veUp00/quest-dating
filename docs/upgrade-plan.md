## Стратегия (без изменений)

1. **Сначала фундамент.** Пока в коде есть P0-уязвимости и мокированные тесты,
   любая продуктовая фича рискует сломать прод или утечь данными.
2. **Потом главная фича.** AI-опросник через DeepSeek — единственное реальное
   конкурентное преимущество, важнее редизайна.
3. **Потом продукт.** Редизайн плеера, сценарии с фото, аудит мини-игр —
   делается после того, как опросник стабильно работает и даёт нормальные данные.

## Фаза 2 — AI-опросник через DeepSeek

Цель: заменить статичную форму заказа на интерактивный AI-диалог,
который собирает данные и **автоматически заполняет шаблон квеста**.

### 2.1. Требует brainstorm с Claude

Открытые вопросы для проработки через `/brainstorming`:

1. **Какие поля шаблона квеста заполняет AI?**
   - Текущая структура `quest_template.fields` — какая она?
   - Какие данные клиента нужны для уникализации:
     - Имена партнёров, дата знакомства
     - Локации (любимые места, район проживания)
     - Общие воспоминания, инсайды
     - Тон квеста (романтичный / детектив / приключение)
     - Фото партнёра (для иммерсии в сценах)
   - Какие поля **обязательны**, какие AI может оставить пустыми

2. **Как AI ведёт диалог?**
   - Фиксированный сценарий вопросов или адаптивный?
   - Сколько вопросов? Можно ли пропускать?
   - Что делать, если клиент даёт мусорные ответы или троллит?
   - Прерывание и возврат к диалогу позже

3. **Где запускается DeepSeek — фронт или бэк?**
   - **Бэк:** защита API-ключа, логирование, rate limiting, версионирование промптов
   - MCP-подключение для разработки vs production-вызовы — разные сценарии
   - Стриминг ответов (UX лучше) или ждать полный ответ

4. **Архитектура UX:**
   - Заменяем `order/[templateSlug].vue` или это новая страница `order/[templateSlug]/ai`?
   - Сохранение прогресса при потере соединения (важно — мобильные пользователи)
   - Как клиент видит "что AI понял" перед оплатой
   - Возможность переписать ответ или начать заново

5. **Валидация результата:**
   - AI заполнил поля → клиент видит превью → подтверждает
   - Admin потом может править результат вручную через админку
   - Что если AI заполнил поле некорректно (например, имя партнёра как "Любимая")

### 2.2. Возможная переделка БД (если потребуется)

Если в ходе brainstorm станет ясно, что текущая схема `quest_templates` не
поддерживает нужную структуру полей — здесь же делаем миграцию:

- Добавление таблицы `ai_conversations` (история диалогов)
- Возможно: рефакторинг `quest_template.fields` (jsonb-структура)
- Возможно: новая таблица `quest_orders_ai_data` (что AI собрал отдельно от заказа)

**Решение принимаем после brainstorm.** Если миграция нужна — оформляется
отдельной задачей с обязательным rollback-планом.

## Правила работы

1. **Каждая задача — отдельная ветка** от `production`, имя `upgrade/<short-name>` или `docs/<short-name>` для документации
2. **Перед `git checkout -b`** — `git checkout production && git pull origin production && git branch --show-current` (проверка)
3. **После `git checkout -b`** — снова `git branch --show-current` (убедиться что переключились)
4. **TDD где возможно:** сначала тест, потом код (используем GSD-подход через Claude Code + Superpowers)
5. **Маленькие коммиты:** один логический шаг = один коммит
6. **Conventional commits format:** `тип(scope): description`
   - типы: feat, fix, refactor, docs, chore, test, style
   - scope опционален: `chore(deps)`, `fix(security)`, `feat(health)`
7. **Перед мержем в `production`:** CI зелёный (когда настроим) + ручная проверка
8. **После мержа:** деплой через `git pull && docker compose build && up -d` на VPS
9. **Перед удалением чего-либо крупного:** git tag для возможности отката (`git tag pre-<what>`)
10. **Перед `npm install`-операцией:** baseline тестов и build, чтобы видеть регрессии
